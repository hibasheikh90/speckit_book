### Section B: Short Answer (10 questions × 2 points = 20 points)

#### Question 21
**Explain the difference between topics and services. When would you use each? (4-6 sentences)**

<details>
<summary>Sample Answer</summary>
Topics use publish/subscribe for continuous, asynchronous data streaming where publishers don't wait for responses. They're ideal for sensor data like camera feeds or lidar scans. Services use request/response for on-demand operations where the client needs an immediate result, like computing inverse kinematics or querying system state. Services are synchronous (client waits), while topics are asynchronous. Use topics for continuous data, services for one-time queries or commands.
</details>

---

#### Question 22
**What is Quality of Service (QoS) and why is it important in ROS 2? Provide one example. (3-4 sentences)**

<details>
<summary>Sample Answer</summary>
QoS policies control message delivery characteristics like reliability, durability, and history. They're critical for ensuring robot systems behave correctly under different network conditions. For example, robot velocity commands should use Reliable QoS to ensure no commands are lost (safety-critical), while high-frequency sensor data can use Best Effort QoS since occasional missed frames are acceptable.
</details>

---

#### Question 23
**Describe the node lifecycle states and when you would use managed nodes. (3-4 sentences)**

<details>
<summary>Sample Answer</summary>
Managed nodes transition through Unconfigured → Inactive → Active states, providing structured startup/shutdown. Unconfigured means resources allocated but not configured, Inactive means configured but not processing, and Active means fully operational. Use managed nodes for production systems requiring coordinated startup sequences, like sensor calibration before data capture, or safety-critical systems needing explicit activation.
</details>

---

#### Question 24
**What is the purpose of parameter callbacks? Provide a use case. (3-4 sentences)**

<details>
<summary>Sample Answer</summary>
Parameter callbacks are called when parameters are updated at runtime, allowing nodes to react to configuration changes without restarting. They enable validation of new parameter values before applying them, returning success/failure. Example use case: a robot controller with a max_speed parameter can validate that new speed values are within safe limits (0-3 m/s) and reject invalid values, preventing dangerous configurations.
</details>

---

#### Question 25
**Explain how topic remapping helps when running multiple robots. (2-3 sentences)**

<details>
<summary>Sample Answer</summary>
Topic remapping changes topic names without modifying code, preventing conflicts when running multiple robot instances. For example, two robots can both publish to `/cmd_vel` internally, but remapping changes them to `/robot1/cmd_vel` and `/robot2/cmd_vel` at launch time. This allows reusable code across different robot configurations.
</details>

---

#### Question 26
**What is an action server's execute callback responsible for? List 3 key responsibilities.**

<details>
<summary>Sample Answer</summary>
1. Execute the goal's task (e.g., navigate to waypoint)
2. Publish feedback periodically to update client on progress
3. Check for cancellation requests and handle gracefully
4. Set final result and mark goal as succeeded/aborted/canceled
</details>

---

#### Question 27
**Why would you use a MultiThreadedExecutor instead of SingleThreadedExecutor?**

<details>
<summary>Sample Answer</summary>
Use MultiThreadedExecutor when you have callbacks that perform blocking operations (e.g., heavy computation, waiting for sensor data). It prevents one slow callback from blocking other callbacks by running them in parallel on different threads. This maintains responsiveness in nodes with mixed fast/slow callbacks.
</details>

---

#### Question 28
**List 4 benefits of using launch files instead of manually starting nodes.**

<details>
<summary>Sample Answer</summary>
1. Reproducible configuration - same setup every time
2. Single command to start entire system
3. Easier to share and version control
4. Coordinated shutdown - all nodes stop together
5. Parameters and remapping configured in one place
</details>

---

#### Question 29
**What command would you use to save all current parameter values of a node to a file?**

<details>
<summary>Sample Answer</summary>
`ros2 param dump /node_name > params.yaml`

This captures the current state of all parameters for backup or sharing.
</details>

---

#### Question 30
**Explain the difference between Reliable and Best Effort QoS. Give one use case for each.**

<details>
<summary>Sample Answer</summary>
Reliable QoS guarantees message delivery through retries and acknowledgments, while Best Effort may lose messages but has lower overhead. Use Reliable for robot commands (e.g., emergency stop) where lost messages are dangerous. Use Best Effort for high-frequency sensor data (e.g., 30Hz camera) where missing occasional frames is acceptable.
</details>

#### 2. Battery Monitor Node (10 points)

**File**: `battery_monitor.py`

**Requirements**:
- Publish battery level to `/battery/level` (Float32)
- Start at 100%, decrease by 0.5% every second
- Parameters:
  - `initial_charge`: 100.0
  - `drain_rate`: 0.5 (% per second)
- Log WARN when &lt;20%, ERROR when &lt;10%
- Publish at 1 Hz

**Evaluation**:
- [2 pts] Correct topic and message type
- [2 pts] Parameters implemented
- [2 pts] Battery decreases correctly
- [2 pts] Logging levels correct
- [2 pts] Clean code and comments

---

#### 3. Navigation Controller Node (15 points)

**File**: `navigation_controller.py`

**Requirements**:
- Subscribe to `/battery/level`
- Publish velocity commands to `/cmd_vel` (Twist)
- Parameters:
  - `max_speed`: 1.0 (m/s)
  - `low_battery_threshold`: 20.0 (%)
- Behavior:
  - Normal operation: publish forward velocity (linear.x = max_speed)
  - Low battery (&lt;threshold): reduce speed to 50%
  - Critical battery (&lt;10%): stop (linear.x = 0)
- Publish at 10 Hz

**Evaluation**:
- [3 pts] Subscription and callback correct
- [3 pts] Publishing velocity commands
- [3 pts] Parameters implemented
- [3 pts] Battery-based speed logic correct
- [3 pts] Clean code and error handling

---

#### 4. Delivery Manager Action Server (15 points)

**File**: `delivery_manager.py`

**Requirements**:
- Action server: `/deliver_package`
- Use `Fibonacci` action (for simplicity) or create custom
- Goal: Delivery location ID (integer)
- Feedback: Distance remaining, percent complete
- Result: Success status
- Behavior:
  - Simulate 10-second delivery
  - Send feedback every second (90%, 80%, ... 0%)
  - Support cancellation
  - Check battery level before accepting goal (reject if &lt;15%)

**Evaluation**:
- [3 pts] Action server created correctly
- [3 pts] Feedback published periodically
- [3 pts] Cancellation handling
- [3 pts] Battery check before acceptance
- [3 pts] Result returned correctly

#### 5. Emergency Stop Service (5 points)

### Testing and Validation

**Test Sequence**:

```bash
# Terminal 1: Launch system
ros2 launch delivery_robot delivery_system_launch.py

# Terminal 2: Verify nodes
ros2 node list  # Should see all 4 nodes

# Terminal 3: Check battery
ros2 topic echo /delivery_robot/battery/level

# Terminal 4: Monitor velocity
ros2 topic echo /delivery_robot/cmd_vel

# Terminal 5: Send delivery goal
ros2 action send_goal /delivery_robot/deliver_package \
    example_interfaces/action/Fibonacci "{order: 5}"

# Terminal 6: Test emergency stop
ros2 service call /delivery_robot/emergency_stop std_srvs/srv/Trigger

# Terminal 7: Test with different battery
ros2 launch delivery_robot delivery_system_launch.py initial_battery:=15.0
```

**Expected Behavior**:
1. Battery decreases from 100% to 0% over 200 seconds
2. Speed reduces at 20% battery
3. Robot stops at 10% battery
4. Delivery action completes in 10 seconds with feedback
5. Delivery rejected if battery &lt;15%
6. Emergency stop immediately zeroes velocity
