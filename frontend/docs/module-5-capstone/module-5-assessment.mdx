### Section B: Short Answer (10 questions × 2 points = 20 points)

#### Question 21
**Describe the five layers of the autonomous humanoid system architecture and their responsibilities. (5-6 sentences)**

<details>
<summary>Sample Answer</summary>
The five layers are: (1) **User Interface Layer** - accepts natural language commands and displays monitoring dashboard (RViz2). (2) **Planning Layer** - contains VLA task planner, MoveIt 2 motion planner, and Nav2 navigation planner for high-level decision making. (3) **Perception Layer** - processes multi-camera images, runs object detection (YOLO), depth estimation, and state estimation (EKF) to build scene representation. (4) **Control Layer** - implements whole-body controller, arm controllers, hand controllers, and locomotion controller for 30+ DOF coordination. (5) **Hardware Layer** - the physical humanoid robot with sensors (cameras, IMU, encoders) and actuators (motors), plus onboard compute (Jetson Orin).
</details>

#### Question 22
**Explain how the ROS 2 Bridge integrates Isaac Sim with robot software. (3-4 sentences)**

<details>
<summary>Sample Answer</summary>
The ROS 2 Bridge enables bidirectional communication between Isaac Sim and ROS 2 nodes. It publishes simulated sensor data (camera images, joint states, IMU readings, clock) as ROS 2 topics that software nodes can subscribe to. It also subscribes to control command topics (joint position commands, velocity commands) and applies them to the simulated robot in Isaac Sim. This allows the entire robot software stack to run identically in simulation and on real hardware, enabling safe testing before deployment.
</details>

#### Question 23
**What are the three types of system requirements? Provide one example of each for a humanoid robot. (4-5 sentences)**

<details>
<summary>Sample Answer</summary>
**Functional Requirements (FR)** - what the system must do. Example: "System SHALL grasp objects weighing 0.1-5 kg with &lt;3cm placement error." **Non-Functional Requirements (NFR)** - how well the system performs. Example: "VLA inference latency SHALL be &lt;100ms for 10Hz control." **Safety Requirements (SR)** - constraints preventing harm. Example: "System SHALL trigger emergency stop within 100ms if fall is detected by IMU." Together, these requirements define complete system specifications for design, implementation, and testing.
</details>

#### Question 25
**What is whole-body control and why is it necessary for humanoid manipulation? (3-4 sentences)**

<details>
<summary>Sample Answer</summary>
Whole-body control coordinates all 30+ degrees of freedom (legs, torso, arms, hands) simultaneously to achieve manipulation goals while maintaining balance. Unlike fixed-base robot arms, humanoids must adjust their torso and leg positions during arm motions to keep the Center of Mass within the support polygon. The controller implements a hierarchy: body-level control maintains balance and posture, arm-level control reaches targets, and hand-level control executes grasps. Without whole-body coordination, humanoids would fall when reaching for objects.
</details>

#### Question 27
**Explain the difference between MoveIt 2 and Nav2 in robot planning. When would you use each?**

<details>
<summary>Sample Answer</summary>
**MoveIt 2** is for manipulator motion planning - it generates collision-free trajectories for robot arms in task space (Cartesian coordinates) or joint space, considering obstacles and self-collision. Use MoveIt 2 when planning arm reaching motions, pick-and-place tasks, or dexterous manipulation. **Nav2** is for mobile robot navigation - it computes safe paths through 2D environments and generates velocity commands for the base, handling dynamic obstacles. Use Nav2 when planning locomotion (walking to target locations) for the humanoid's mobile base. Often both are used together: Nav2 gets the humanoid to the workspace, MoveIt 2 plans the manipulation.
</details>

---

#### Question 28
**What is the purpose of system integration testing? List 3 types of integration tests for the capstone.**

<details>
<summary>Sample Answer</summary>
System integration testing validates that all components work correctly together as a complete system, catching interface bugs and timing issues not visible in unit tests. Three integration tests: **(1) Perception-VLA integration test** - verify camera images → YOLO detections → VLA scene understanding produces correct task decomposition. **(2) VLA-Control integration test** - verify VLA action outputs → controller joint commands execute without collisions or instability. **(3) End-to-end task test** - full pipeline from language command → perception → planning → control → task completion, measuring overall success rate and latency.
</details>

---

#### Question 29
**Describe three safety requirements for autonomous humanoid robots operating in human environments.**

<details>
<summary>Sample Answer</summary>
1. **Fall Detection and Recovery (SR-1)**: Monitor IMU for abnormal accelerations (>2g) indicating loss of balance. Trigger emergency stop within 100ms, retracting arms to protective position and cutting motor power.
2. **Collision Avoidance (SR-2)**: Maintain minimum 20cm safety margin from obstacles (walls, furniture, humans) using costmap from depth sensors. Reduce arm velocity to &lt;0.1 m/s when humans detected within 1m radius.
3. **Joint Protection (SR-3)**: Enforce software joint limits with 5° safety margin from hardware limits. Monitor motor temperatures and throttle to 50% torque if exceeding 70°C to prevent overheating damage.
</details>

---

#### Question 30
**What is the role of performance profiling in system validation? What metrics should be measured?**

<details>
<summary>Sample Answer</summary>
Performance profiling measures system resource usage and timing to validate that non-functional requirements are met and identify bottlenecks. Key metrics: **(1) Latency** - VLA inference time, perception pipeline latency, end-to-end command-to-action time. **(2) Throughput** - control loop frequency (Hz), camera frame rate, message publication rates. **(3) Resource usage** - CPU utilization per node, GPU memory consumption, RAM usage, network bandwidth. **(4) Real-time constraints** - worst-case execution time, deadline misses, jitter in control loop. These metrics ensure the system meets &lt;100ms latency targets and >10Hz control frequency for safe real-time operation.
</details>

## Part 2: Capstone Project (60 points)

### Project: Autonomous Warehouse Assistant Humanoid

Build a complete autonomous humanoid robot system that navigates to shelves, manipulates objects, and responds to natural language commands in a warehouse environment.

**Time**: 60 minutes (this is a design and partial implementation assessment)

---

### System Specification

**Scenario**: Warehouse assistant robot receives commands like:
- "Bring me the blue box from shelf A"
- "Place all red items on the sorting table"
- "Organize the tools on the workbench"

**Robot**: Simulated humanoid in Isaac Sim (Unitree G1 or similar)
- 30 DOF (legs, torso, arms, hands)
- 3 cameras (head, left wrist, right wrist)
- IMU for balance
- Parallel grippers (1-DOF each hand)

**Environment**: Warehouse with 3 shelves, objects of varying colors/shapes, obstacles

---

### Project Requirements

#### Phase 1: System Architecture Design (15 points)

**Tasks**:
1. Create complete system architecture diagram showing:
   - All ROS 2 nodes (minimum 8 nodes required)
   - Topics, services, actions connecting nodes
   - External dependencies (Isaac Sim, TensorRT models)
   - Data flow from command input → task execution

2. Define ROS 2 node architecture:
   ```
   Required Nodes:
   - vision_encoder_node (CLIP)
   - language_encoder_node (T5)
   - object_detector_node (YOLO)
   - state_estimator_node (EKF)
   - vla_planner_node (task decomposition)
   - motion_planner_node (MoveIt 2 wrapper)
   - whole_body_controller_node
   - safety_monitor_node
   ```

3. Specify topic/service interfaces:
   - Camera topics: `/head_camera/image_raw`, `/left_wrist_camera/image_raw`, `/right_wrist_camera/image_raw`
   - Command topic: `/task/command` (String)
   - Action topics: `/left_arm/action`, `/right_arm/action`, `/body/action`
   - Safety service: `/emergency_stop` (Trigger)
   - State topic: `/robot/state` (JointState + IMU)

**Deliverables**:
- Architecture diagram (Mermaid or draw.io)
- Node interface specifications (topics/services/actions)
- Data flow diagram

**Evaluation**:
- [5 pts] Complete architecture with all required nodes
- [5 pts] Correct topic/service/action interfaces
- [5 pts] Clear data flow and dependencies

---

#### Phase 2: Perception Pipeline Implementation (15 points)

**Tasks**:
1. Implement `object_detector_node.py`:
   - Subscribe to `/head_camera/image_raw`
   - Load YOLOv8 model (pre-trained on COCO)
   - Detect objects: boxes, shelves, obstacles
   - Publish detections to `/perception/detections` (custom message with bounding boxes, class, confidence)
   - Run at 20 Hz

2. Implement `vision_encoder_node.py`:
   - Subscribe to multi-camera topics (3 cameras)
   - Fuse images into single representation
   - Encode with CLIP ViT-B/32
   - Publish to `/perception/vision_embedding`

3. Implement `state_estimator_node.py`:
   - Subscribe to `/imu/data` and `/joint_states`
   - Implement simple EKF for pose estimation
   - Publish estimated CoM position
   - Publish balance state (stable/unstable)

**Deliverables**:
- 3 Python node files with complete implementations
- Launch file for perception stack
- Test results showing detection accuracy and runtime

**Evaluation**:
- [5 pts] Object detector running with >80% mAP
- [5 pts] Vision encoder fusing multi-camera input
- [5 pts] State estimator publishing CoM and balance state

---

#### Phase 3: VLA Integration and Planning (15 points)

**Tasks**:
1. Implement `vla_planner_node.py`:
   - Subscribe to vision embeddings + language command
   - Load simplified VLA policy (can use rule-based for time constraint)
   - Decompose task into subtasks:
     ```
     "Bring blue box" → [navigate_to_shelf, detect_blue_box, grasp, navigate_to_person, release]
     ```
   - Publish subtask sequence to `/planner/task_sequence`

2. Implement `motion_planner_node.py`:
   - Subscribe to `/planner/task_sequence`
   - For each subtask, generate motion plan:
     - `grasp` → compute IK for arm reaching
     - `navigate` → call Nav2 for path
   - Publish trajectories to `/motion/trajectory`

3. Test command understanding:
   - Test 5 commands:
     1. "Pick up the red cube"
     2. "Place the box on shelf B"
     3. "Bring me the tool"
     4. "Move to the sorting table"
     5. "Organize items by color"

**Deliverables**:
- VLA planner node
- Motion planner node
- Test report showing task decomposition for 5 commands

**Evaluation**:
- [6 pts] VLA planner correctly decomposes tasks
- [5 pts] Motion planner generates valid trajectories
- [4 pts] Successfully handles 5 test commands

---

#### Phase 4: Whole-Body Control (10 points)

**Tasks**:
1. Implement `whole_body_controller_node.py`:
   - Subscribe to `/motion/trajectory`
   - Implement hierarchical control:
     - Body controller: maintain balance (adjust torso/legs)
     - Arm controller: execute reaching motions
     - Hand controller: gripper open/close
   - Check balance constraint before each motion
   - Publish joint commands to `/joint_position_controller/commands`

2. Implement `safety_monitor_node.py`:
   - Subscribe to `/imu/data`, `/joint_states`, `/perception/detections`

**Deliverables**:
