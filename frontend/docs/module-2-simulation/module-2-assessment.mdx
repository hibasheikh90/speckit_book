### Section B: Short Answer (20 points, 4 points each)

#### Question 11
**Explain the difference between `<visual>` and `<collision>` elements in URDF. Why might they differ?**

**Expected Answer** (75-100 words):
- `<visual>`: Defines the visual appearance (meshes, colors) displayed in simulation/rviz
- `<collision>`: Defines simplified geometry used for physics collision detection
- **Why differ**: Collision geometry should be simpler (boxes, cylinders) for performance, while visual can use detailed meshes (.stl, .dae) for realism
- Example: A robot arm might have complex visual mesh but simple cylindrical collision shapes
- Keeps simulation fast while maintaining visual fidelity

#### Question 12
**What are the three main challenges in sim-to-real transfer, and how can simulation help address them?**

**Expected Answer** (100-125 words):
1. **Sensor noise**: Real sensors have noise. Solution: Add Gaussian noise to simulated sensors (camera, lidar, IMU)
2. **Physics accuracy**: Simulation physics differ from reality. Solution: Calibrate friction, mass, inertia parameters; test in diverse scenarios
3. **Environmental variation**: Real world is unpredictable. Solution: Create varied environments (lighting, terrain, obstacles) for robust training

**How simulation helps**:
- Rapid iteration without hardware damage
- Automated testing across thousands of scenarios
- Domain randomization for generalization
- Safe failure analysis

#### Question 13
**Describe the Gazebo plugin architecture. How does a sensor plugin communicate with ROS 2?**

**Expected Answer** (100-125 words):
**Architecture**:
- Gazebo plugins are C++ libraries (`.so` files) loaded into Gazebo at runtime
- Types: World, Model, Sensor, Visual, System
- Plugins access Gazebo APIs (physics, sensors, rendering)

**ROS 2 Communication**:
1. Plugin reads simulated sensor data (e.g., camera image from Gazebo's rendering)
2. Converts to ROS 2 message type (`sensor_msgs/Image`)
3. Publishes to ROS 2 topic via `gazebo_ros` bridge
4. ROS 2 nodes subscribe and process data

**Example**: Camera plugin reads rendered image → converts to `sensor_msgs/Image` → publishes to `/camera/image_raw`

#### Question 15
**What is inverse kinematics (IK) and why is it useful for humanoid animation in Unity?**

**Expected Answer** (75-100 words):
**IK Definition**:
- Computes joint angles needed to position an end effector (hand, foot) at a target location
- Opposite of forward kinematics (joint angles → end position)

**Why useful**:
- Natural foot placement on uneven terrain
- Hand reaching for objects (grasping)
- Head tracking (looking at robots)
- Realistic interactions without manual animation

**Example**: When robot hands object to human, IK adjusts human's arm joints so hand reaches exact object position, creating believable interaction.

## Example Starter Code

### Gazebo Launch File

**File: `warehouse_launch.py`**

```python
from launch import LaunchDescription
from launch_ros.actions import Node
from launch.actions import IncludeLaunchDescription
from launch.launch_description_sources import PythonLaunchDescriptionSource
import os

def generate_launch_description():
    # Paths
    world_file = os.path.join(os.getcwd(), 'warehouse.world')
    urdf_file = os.path.join(os.getcwd(), 'delivery_robot.urdf.xacro')

    return LaunchDescription([
        # Start Gazebo
        IncludeLaunchDescription(
            PythonLaunchDescriptionSource([
                '/opt/ros/humble/share/gazebo_ros/launch/gazebo.launch.py'
            ]),
            launch_arguments={'world': world_file}.items()
        ),

        # Spawn robot
        Node(
            package='gazebo_ros',
            executable='spawn_entity.py',
            arguments=['-entity', 'delivery_robot', '-file', urdf_file],
            output='screen'
        ),

        # Navigation node
        Node(
            package='warehouse_sim',
            executable='warehouse_navigator.py',
            output='screen'
        ),
    ])
```

### Unity ROS Subscriber Template

**File: `RobotVisualizer.cs`**

```csharp
using UnityEngine;
using Unity.Robotics.ROSTCPConnector;
using RosMessageTypes.Nav;

public class RobotVisualizer : MonoBehaviour
{
    public string odomTopic = "odom";
    public GameObject robotSphere;

    void Start()
    {
        ROSConnection.GetOrCreateInstance().Subscribe<OdometryMsg>(odomTopic, OnOdomReceived);
    }

    void OnOdomReceived(OdometryMsg msg)
    {
        // Update robot sphere position
        Vector3 position = new Vector3(
            (float)msg.pose.pose.position.x,
            (float)msg.pose.pose.position.y,
            (float)msg.pose.pose.position.z
        );
        robotSphere.transform.position = position;
    }
}
```

## Frequently Asked Questions

**Q: Can I use an existing warehouse model from Gazebo's model database?**
A: You may use individual components (racks, pallets), but the overall world layout must be your original design.

**Q: Do I need to implement full SLAM or Nav2?**
A: No, basic obstacle avoidance and waypoint navigation is sufficient. Bonus points for Nav2 integration.

**Q: Can I work in a team?**
A: Check with your instructor. If allowed, clearly specify each member's contributions.

**Q: What if Gazebo crashes frequently?**
A: Reduce world complexity, disable shadows, or run in headless mode. Document this in README.

**Q: Unity won't connect to ROS-TCP-Endpoint?**
A: Verify firewall settings, check IP/port configuration, ensure endpoint is running before Unity Play.
