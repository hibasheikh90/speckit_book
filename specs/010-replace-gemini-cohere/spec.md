# Feature Specification: Replace Gemini with Cohere API

**Feature Branch**: `010-replace-gemini-cohere`
**Created**: 2025-12-24
**Status**: Draft
**Input**: User description: "I am NOT using Gemini anymore. I am using Cohere API for my chatbot. Remove Gemini completely. Integrate Cohere API for all chat responses. Do not change routes, database, auth, or frontend. Only replace AI provider layer. Return full updated backend code."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - AI Provider Migration (Priority: P1)

As a system administrator, I need the chatbot backend to use Cohere API instead of Gemini API for generating chat responses, so that the system uses the correct AI service without affecting existing functionality.

**Why this priority**: This is the core requirement. The chatbot must switch AI providers while maintaining all existing behavior for end users.

**Independent Test**: Can be fully tested by sending chat requests to the `/chat` endpoint and verifying that responses come from Cohere API. The functionality delivers the same chat experience with a different AI backend.

**Acceptance Scenarios**:

1. **Given** the backend is running with Cohere API configured, **When** a user sends a chat message, **Then** the response is generated by Cohere API and returned successfully
2. **Given** the Cohere API key is properly configured, **When** the application starts up, **Then** the AI agent initializes successfully with Cohere client
3. **Given** a chat request is made, **When** Cohere API generates a response, **Then** the response format matches the existing ChatResponse model structure

---

### User Story 2 - Configuration Migration (Priority: P1)

As a developer, I need all Gemini-specific configuration removed and replaced with Cohere-specific settings, so that the system has no remaining dependencies on Gemini.

**Why this priority**: Configuration must be updated to prevent any accidental calls to deprecated Gemini endpoints and to properly authenticate with Cohere.

**Independent Test**: Can be tested by reviewing environment variables and settings files to confirm no Gemini references remain, and by validating that Cohere API credentials are properly loaded.

**Acceptance Scenarios**:

1. **Given** the environment configuration file, **When** reviewing API keys and endpoints, **Then** only Cohere API credentials exist with no Gemini references
2. **Given** the settings module, **When** loading configuration at startup, **Then** Cohere-specific settings (API key, base URL, model name) are properly validated and loaded
3. **Given** the health check endpoint, **When** queried, **Then** it reports Cohere model information instead of Gemini

---

### User Story 3 - Backward Compatibility (Priority: P2)

As an end user or frontend developer, I need the chat API contract to remain unchanged, so that existing integrations continue to work without modification.

**Why this priority**: While the AI provider changes internally, the external interface must remain stable to avoid breaking changes.

**Independent Test**: Can be tested by using the existing frontend application or API tests against the updated backend to verify identical request/response formats.

**Acceptance Scenarios**:

1. **Given** an existing chat request payload, **When** sent to the `/chat` endpoint, **Then** the response structure matches the original ChatResponse format
2. **Given** the frontend chat interface, **When** users interact with the chatbot, **Then** the experience is identical to before the migration
3. **Given** existing error handling, **When** API failures occur, **Then** error responses maintain the same format and status codes

---

### Edge Cases

- What happens when Cohere API key is missing or invalid at startup?
- How does the system handle Cohere API rate limits or quota exceeded errors?
- What happens when Cohere API is temporarily unavailable?
- How does the system handle timeout scenarios with Cohere API?
- What happens if Cohere returns an empty or malformed response?

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST remove all Gemini API client code and dependencies
- **FR-002**: System MUST integrate Cohere API client for chat response generation
- **FR-003**: System MUST use Cohere API key from environment configuration
- **FR-004**: System MUST preserve existing `/chat` endpoint route and request/response contracts
- **FR-005**: System MUST preserve existing database schema and authentication mechanisms
- **FR-006**: System MUST initialize Cohere client at application startup
- **FR-007**: System MUST handle Cohere API errors gracefully with appropriate fallback messages
- **FR-008**: System MUST maintain existing timeout behavior (30 seconds default)
- **FR-009**: System MUST update health check endpoint to report Cohere model information
- **FR-010**: System MUST remove all Gemini-specific configuration variables and replace with Cohere equivalents
- **FR-011**: System MUST maintain existing rate limiting behavior (10 requests/minute default)
- **FR-012**: System MUST preserve agent instructions/constitution loading mechanism
- **FR-013**: System MUST maintain the same response format (ChatResponse model) for frontend compatibility

### Key Entities

- **AITutor Agent**: The core agent class that generates chat responses using the Cohere API client instead of Gemini
- **Cohere Client**: The HTTP client configured to communicate with Cohere API endpoints
- **Settings Configuration**: Environment-based configuration storing Cohere API credentials, model name, and base URL
- **ChatRequest/ChatResponse**: Request and response data models that remain unchanged for API contract stability

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: All chat requests generate responses from Cohere API with 100% of calls routed to Cohere endpoints
- **SC-002**: Application startup succeeds with Cohere client initialization in under 5 seconds
- **SC-003**: Chat response times remain comparable to or better than Gemini implementation (within 10% variance)
- **SC-004**: Zero breaking changes to frontend - existing chat interface works without modification
- **SC-005**: Health check endpoint reports accurate Cohere model information
- **SC-006**: Error handling maintains existing user experience with appropriate fallback messages
- **SC-007**: No Gemini-related code or configuration remains in the codebase (verified by code search)
- **SC-008**: All environment variables are updated to reflect Cohere credentials with no Gemini references

## Assumptions *(if applicable)*

- Cohere API credentials (API key) are available and properly configured in environment
- Cohere API provides comparable chat completion capabilities to Gemini
- Cohere API supports streaming or non-streaming responses compatible with current implementation
- The existing agents-sdk or similar framework can be adapted for Cohere, or a native Cohere client will be used
- Cohere API has sufficient rate limits and quotas for the application's usage patterns
- The constitution/instructions loading mechanism works identically regardless of AI provider
- Existing tools integration (textbook search) can be preserved or adapted for Cohere

## Dependencies *(if applicable)*

- Cohere Python SDK or HTTP client library
- Valid Cohere API key with appropriate access permissions
- Cohere API service availability and uptime
- Removal of agents-sdk dependency if it's Gemini-specific, or adaptation to support Cohere

## Out of Scope

- Changes to frontend chat interface or components
- Modifications to database schema or models
- Updates to authentication or authorization mechanisms
- Changes to API routes, endpoints, or URL structure
- Performance optimization beyond provider replacement
- Addition of new chatbot features or capabilities
- Migration of historical chat data or conversation logs
- A/B testing or gradual rollout strategy
- Monitoring or analytics changes
